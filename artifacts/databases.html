What each group does, and why it's shaped that way

The grouping isn't cosmetic — it mirrors the seven ideas Mission.md and SiteShape.md actually separate from each other.

Identity & Bots

users · bot_personas

One users table for humans and bot personas alike — is_bot is just a flag, not a parallel schema, because Mission.md treats bots as residents of the same space, not a different kind of thing.

The server never stores your drawn ID, only image_hash (a SHA-256 of it). That's the whole login: no password column exists to leak, and there's no recovery table either — losing the PNG is permanent, by design.

Public Stream

posts

Every visible thing on the site — a message, a bot's welcome note, a redeemed-gift announcement — is one row here, distinguished only by kind. There's no separate "announcements" or "system messages" table, because SiteShape.md treats them all as peers in one flat, chronological feed.

Gift Economy

gift_notes

A note doesn't move between rows as it's passed hand to hand — current_holder_id just gets overwritten, while original_author_id never changes. That's how a note can pass through five people and still visibly trace back to whoever first gave it.

redeemed_at is the only field that turns a private note into a public one (a posts row with kind='redemption') — and it's write-once. Redeemed is a one-way door.

Messaging & Notifications

message_threads · messages · notifications

Person-to-person and person-to-bot conversations both live in message_threads/messages — the only difference is the is_bot_thread flag, which is what lets bots read bot conversations and never human-to-human ones, per Mission.md's hard privacy rule.

notifications is kept deliberately separate from messages — a "your note was redeemed" ping is a system notice, never a conversation, so it never risks looking like one.

Bot Intelligence

user_facts · coordinator_notices

user_facts is a bot's memory in the literal sense Mission.md means it: "the database is the memory, not the context window." A fact is only ever extracted from a human→bot thread (source_thread_id), never a human-to-human one.

coordinator_notices exists purely so a bot doesn't announce the same overlap match to the same person twice — a small dedupe log, not a scoring system.

Social Safety

blocks

One row, one direction: blocker_id stops seeing blocked_id. There's no ratio, no score, no visibility to the blocked person — every query that respects a block has to scope itself to "as viewed by the current user," never a global exclusion, exactly as Mission.md insists blocking stay personal, not a platform punishment.

Site Meta

site_meta

A plain key–value table with no foreign keys at all — the one deliberately un-networked table, left over from the original project skeleton for whatever small global settings show up later.

What's preserved for later

A handful of columns and choices exist that nothing reads yet — each one is a seam left open on purpose, so a future feature slots in without a schema rewrite.

bot_personas.prompt

Stored at signup time but nothing ever sends it to a real LLM yet. When a persona gets an actual generated voice, the column's already there.

message_threads.is_bot_thread

Set to 0 on every row so far — nothing routes a thread as bot-vs-human yet. It's the flag SiteShape.md's "visibly different surfaces" rule will hang off once bot conversations actually start.

posts.author_name

Kept alongside the newer author_id rather than dropped — it's what pre-account posts from the placeholder-identity era still carry, so old rows don't need a backfill to stay readable.

users.is_bot

A flag instead of a second table — the deliberate choice that keeps humans and bots sharing one identity system, the way Mission.md's "humans and bots share this space" actually wants it modeled.

avatar files, not a table

Derived avatars live as plain PNG files on disk, named by user id — not a database row. Nothing stops a future avatars table from replacing that if avatars ever need more than one file per person.

user_facts.key / value

Generic on purpose: a new fact type (a channel used, a new kind of need) is just a new key, never a new column or migration.

no location columns yet

SiteShape.md's proximity shading needs a rough lat/lon somewhere on users — not built yet, and deliberately absent rather than guessed at early.

no moderation table

There's no role, permission, or report table anywhere in this schema. SiteShape.md flags real moderation as a genuinely open question — the schema reflects that honestly instead of pre-building an admin system nobody's decided on.
